WHY THIS PAGE IS THE ANSWER TO "CAN YOU PROVE IT" Every other page in the project makes a claim: an employee did some work, an action waited for a person, an integration simulated rather than sent. This is where those claims are checked. Entries are written by marketing/audit.py and never edited, so the table is a record rather than a report. A SIMULATED ACTION MUST NOT LOOK LIKE A REAL ONE The five outcomes are coloured and shaped differently, not just labelled: Succeeded, Simulated, Failed, Denied and Pending. Somebody scanning the column has to be able to see at a glance that a row was a simulation, and a green tick beside "email sent" that actually means "email pretended" is the single worst thing this page could do. FILTERS ARE GET PARAMETERS Every filter is a query parameter and the form is a plain GET form, so a narrowed view is a URL somebody can send to a colleague, the browser back button works, and the page needs no JavaScript at all. The view rebuilds the same parameters into `querystring` so the pagination links carry them. THE DETAIL PAYLOAD Each entry's JSON detail is behind a
element rather than a JavaScript toggle. Fifty collapsible cells that work with scripting switched off are worth more than a bespoke widget. {% endcomment %} {% block title %}Audit log | AI Workforce{% endblock %} {% block body_class %}page-audit{% endblock %} {% block page_title %}Audit log{% endblock %} {% block page_subtitle %} Everything the platform did, who or what did it, and whether it really happened or was simulated. {% endblock %} {% block page_actions %} Integrations {% if actions_url %} Action queue {% endif %} {% endblock %} {% block content %}
